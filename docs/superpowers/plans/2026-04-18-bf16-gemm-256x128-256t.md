New header:
```
/***************************************************************************************************
 * BF16 GEMM using SM80 tensor cores with CuTe — (256, 128, 64) Tile, 256 Threads
 *
 * A variant of bf16_gemm_sm80_pipe.cu that doubles the M tile dimension (256 vs 128)
 * and doubles the thread count (256 vs 128) to keep per-thread register pressure constant.
 *
 * This sample demonstrates how to scale CTA tile sizes without causing register spilling:
 *   - (256, 128, 64) CTA tile with 256 threads (8 warps) instead of (128, 128, 64) with 128
 *   - Per-thread accumulator count remains 128 f32 in both configurations
 *   - The 128-thread version of this tile catastrophically regressed (~4.6 TFLOP/s at 4096^3
 *     vs ~360 TFLOP/s) due to register spilling (256 f32 per thread exceeded 255 register limit)
 *
 * All pipeline features are identical to bf16_gemm_sm80_pipe.cu:
 *   - cp.async asynchronous global-to-shared memory copy (SM80 feature)
 *   - 3-stage software pipeline overlapping gmem->smem with MMA compute
 *   - Dynamic shared memory allocation (extern __shared__)
 *   - TiledCopy for gmem->smem replacing synchronous local_partition
 *   - partition_fragment_A/B for register allocation from pipelined smem
 *
 * C = alpha * A * B^T + beta * C
 *   A: bf16, M x K, row-major (TN layout)
 *   B: bf16, K x N, stored as (N, K) in CuTe with K-contiguous stride
 *   C: f32, M x N, column-major
 *
 * Target: SM80+ tensor cores (runs on SM90 L20Y GPU)
 *
 * Configuration comparison with bf16_gemm_sm80_pipe.cu (128, 128, 64) / 128 threads:
 *
 *   | Parameter           | 128-thread baseline | This sample (256 threads)  |
 *   |---------------------|---------------------|----------------------------|
 *   | CTA tile            | (128, 128, 64)      | (256, 128, 64)             |
 *   | MMA atom layout     | Layout<Shape<2, 2>> | Layout<Shape<4, 2>>        |
 *   | MMA Tile override   | Tile<32, 32, 16>    | Tile<_, 64, _>             |
 *   | Threads             | 128 (4 warps)       | 256 (8 warps)              |
 *   | G2S thread layout   | Layout<Shape<16,8>> | Layout<Shape<32,8>>        |
 *   | Smem sA             | (128,64,3) ≈ 48 KB  | (256,64,3) ≈ 96 KB        |
 *   | Smem sB             | (128,64,3) ≈ 48 KB  | (128,64,3) ≈ 48 KB        |
 *   | Total smem          | ~96 KB              | ~144 KB                    |
 *   | Per-thread accum    | 128 f32             | 128 f32 (identical)        |
 *   | Blocks/SM (192KB)   | 2                   | 1                          |
 *   | Threads/SM          | 256                 | 256 (identical)            |
 *
 * Why Tile<_, _64, _> instead of Tile<_32, _32, _16>:
 *   With Layout<Shape<_4, _2>>, the MMA atom (16×8) is arranged as 4 atoms in M and 2 in N.
 *   Within a (32, 32) sub-tile, the atom creates (2, 4) repeats, but zipped_divide cannot
 *   split (2, 4) by the atom layout (4, 2) since 2 < 4 in M. Tile<_, _64, _> uses default
 *   M (= 16×4 = 64) and explicit N = 64, giving valid sub-tiles (64, 64) with (4, 8) repeats
 *   that zipped_divide correctly splits by (4, 2).
 *
 * Pipeline overview (identical to bf16_gemm_sm80_pipe.cu):
 *   The key insight is that cp.async allows the GPU to load the next K-tile from global
 *   memory into shared memory while the current K-tile is being processed by tensor cores.
 *   We use 3 pipe stages (bP=3): while the MMA works on stage N, cp.async fills stage N+1
 *   and stage N+2 may already be in flight.
 *
 *   Timeline (conceptual):
 *     T0: cp.async load pipe[0] from gmem
 *     T1: cp.async load pipe[1] from gmem | wait for pipe[0] | smem->regs | MMA on pipe[0]
 *     T2: cp.async load pipe[2] from gmem | wait for pipe[1] | smem->regs | MMA on pipe[1]
 *     T3: cp.async load pipe[0] from gmem | wait for pipe[2] | smem->regs | MMA on pipe[2]
 *         ^-- pipe[0] is now free because MMA finished with it
 **************************************************************************************************/
```

```cpp
  // TiledMMA (static)
  //
  // Atom: SM80_16x8x16_F32BF16BF16F32_TN — 16x8x16 BF16*BF16->F32, 32 threads
  // Atom layout: 4x2 in (M, N) -> 256 threads total (8 warps)
  //   - 4 atoms in M covers 4*16 = 64 M positions per MMA call
  //   - 2 atoms in N covers 2*8  = 16 N positions per MMA call
  //   - Doubled in M from Layout<Shape<_2,_2>> to distribute the wider (256) tile
  //
  // Tile<_, _64, _> override:
  //   - M: default = 16 * 4 = 64 (atom_M * atoms_in_M)
  //   - N: explicit 64, expands from 16 (2 atoms of 8) to 64 (8 atoms of 8)
  //   - K: default = 16 * 1 = 16 (atom_K * atoms_in_K)
  //   - Required for SM75_U32x4_LDSM_N which needs 4 values per thread
  //
  // Note: Tile<_32, _32, _16> from the 128-thread version does NOT work here.
  //   With Layout<Shape<_4, _2>>, a (32, 32) sub-tile creates (2, 4) atom repeats
  //   (from 32/16=2 in M, 32/8=4 in N). zipped_divide cannot split (2, 4) by the
  //   atom layout (4, 2) since 2 < 4 in M. Using Tile<_, _64, _> gives (64, 64)
  //   sub-tiles with (4, 8) repeats, which correctly divides by (4, 2).

      SM80_16x8x16_F32BF16BF16F32_TN{},
      Layout<Shape<_4, _2>>{},
      Tile<_, _64, _>{});
```
