# Iteration 09: Real Asymmetric W4A16 Example

Per-group asymmetric dequant on top of iter 08: W4A16 with group size 128 along K,
per-(M, K_group) bf16 scales and zero points, applied on the fly in the consumer
kernel via a separate per-group smem pipeline. Mock end-to-end (random uint4 weights
+ random bf16 scales/zeros, CPU reference dequantizes the same way) — no integration
with turbomind's production weight format yet.

**Files (planned):** `cute-reference/mixed-gemm/09_*`

## Goal & scope

Validate that iter 08's pipeline can carry real asymmetric per-group dequant without
losing performance.

In scope:
- Asymmetric quant: `dequant = (q − zero) * scale` per element
- Group size 128 along K (compile-time constant; assert `K % 128 == 0`)
- bf16 scales, bf16 zero points (one (scale, zero) pair per (M, K_group))
- Mock data path: random uint4 in [0,15] for weights and zeros, random bf16 scales

Deferred:
- Turbomind production weight format (packed-uint4 zeros, per-channel layouts)
- Other group sizes (64, 256, 512), symmetric variant, per-tensor / per-channel-only
- Real model weights / quant calibration

Performance bar: hold within ~2 percentage points of iter 08's 86.7% / 94.4% of cuBLAS
at 4096³ / 8192³.

## 1. Test data layout (host)

Three CPU-side arrays:

| Array | dtype | Shape | Notes |
|---|---|---|---|
| `h_A_bf16` | bf16 | `(M, K)` row-major | uint4 value `q ∈ [0,15]` in low 4 bits, same encoding as iter 08 — feeds the unchanged pack kernel |
| `h_scales` | bf16 | `(K/128, M)` row-major | random in `[0.25, 4.0]` |
| `h_zeros` | bf16 | `(K/128, M)` row-major | uint4 `z ∈ [0,15]` cast to bf16; **−128 lop3 bias folded in by host before upload** (see §3) |

The host also keeps integer side-arrays `h_q_int[M*K]` and `h_z_int[(K/128)*M]` (uint8
storage of the underlying uint4 values) for the CPU reference in §5. Iter 08's harness
already does this for `h_q_int` via `h_A_val`; iter 09 adds the same for zeros.

Just before kernel launch, a host helper interleaves scales and (folded) zeros into
a single device buffer for one bulk copy per group:

```cpp
// Layout: d_sz_packed[K_g][M][2], pair = (scale_lo_bf16, eff_zero_hi_bf16) packed as uint32
for (g, m) :
  d_sz_packed[g * M + m] = (uint32(eff_zero_bf16_bits) << 16) | uint32(scale_bf16_bits);
```

Group bulk-copy size: 128 × 4 = **512 B**.

Test sizes: K=64 cases from iter 08 are bumped to K=128 for the group-size precondition.
- Single tile / Multi-M / Multi-N: 128×256×128, 256×256×128, 128×512×128
- Multi-K / Multi-MK: 128×256×256, 256×256×256
- K=4: 128×256×512
- Large / 1024³ / 2048×1024×512: unchanged
- Benchmarks: 4096³, 8192³ (unchanged)

## 2. Pack kernel

**No behavior changes from iter 08.** The pack kernel only reads `h_A_bf16` and
writes the uint4-packed weight buffer. Scales/zeros are independent inputs to the
WGMMA kernel.

For isolation, the iter-08 header is copied to `09_split_a_pack.h` and the iter-09
WGMMA kernel adds a new `unpack_dequant_to_bf16` helper (see §3.2) without touching
iter 08's `unpack_u4_to_bf16` (which still subtracts 128).

## 3. WGMMA register-fragment access pattern

Per warpgroup the A operand uses CuTe `ALayout_64x16` whose codomain is **K-major**
(`linear = k * 64 + m`, verified empirically — see §3.3). Each thread `t` (with
`T0 = t%4`, `T1 = (t/4)%8`, `T2 = t/32`) holds 8 register values whose `(m, k)`
positions are:

| reg | m | k |
|---|---|---|
| 0 | m_lo | 2·T0     |
| 1 | m_lo | 2·T0 + 1 |
| 2 | m_hi | 2·T0     |
| 3 | m_hi | 2·T0 + 1 |
| 4 | m_lo | 2·T0 + 8 |
| 5 | m_lo | 2·T0 + 9 |
| 6 | m_hi | 2·T0 + 8 |
| 7 | m_hi | 2·T0 + 9 |

with `m_lo = T1 + 16·T2`, `m_hi = m_lo + 8`. So per thread per k_block the 8 values
cover **2 distinct M rows × 4 K cols**. After the iter-08 lop3, the four bf16x2
halves are:
- `h[0]` = (reg0, reg1): both **M = m_lo**
- `h[1]` = (reg2, reg3): both **M = m_hi**
- `h[2]` = (reg4, reg5): both **M = m_lo**
- `h[3]` = (reg6, reg7): both **M = m_hi**

Per group, each thread needs **one** scale and **one** eff_zero per M row × 2 rows
= 2 distinct bf16 values. The dequant uses bf16x2 broadcasts (same value in both
halves of each pair).

### 3.1 Per-thread S/Z load

Smem layout per stage: `sz_smem[128]` of uint32 — one entry per M row of the **whole**
CTA tile (M=128), packing `(scale_lo_bf16, eff_zero_hi_bf16)`. Each warpgroup covers
half the rows: WG 0 owns `sz_smem[0..63]`, WG 1 owns `sz_smem[64..127]`. The thread's
WG-local m_lo is in `[0, 56]`, m_hi = m_lo + 8 in `[8, 63]`. The WG base offset
`wg_id * 64` is added for global indexing:

```cpp
int m_lo = wg_id * 64 + (local_tid / 4) % 8 + 16 * (local_tid / 32);
int m_hi = m_lo + 8;

uint32_t r_lo = sz_smem[m_lo];   // (scale_lo, eff_zero_lo) packed as uint32
uint32_t r_hi = sz_smem[m_hi];

// Broadcast each bf16 into both halves of a bf16x2.
uint32_t s_lo = r_lo & 0xFFFFu;          // scale[m_lo]_bf16
uint32_t z_lo = (r_lo >> 16) & 0xFFFFu;  // eff_zero[m_lo]_bf16
uint32_t s_hi = r_hi & 0xFFFFu;
uint32_t z_hi = (r_hi >> 16) & 0xFFFFu;

uint32_t scale_lo_pair = (s_lo << 16) | s_lo;  // bf16x2(scale[m_lo], scale[m_lo])
uint32_t zero_lo_pair  = (z_lo << 16) | z_lo;
uint32_t scale_hi_pair = (s_hi << 16) | s_hi;
uint32_t zero_hi_pair  = (z_hi << 16) | z_hi;
```

2 LDS.32 + 8 register ops (mask/shift/or to broadcast), executed once per group,
cached for 8 k_blocks. The two LDS addresses for thread `t` are 4 bytes apart (one
WG-local row pair), so threads in the same warp hit different banks. Conflict-free.

### 3.3 Empirical verification of the K-major mapping

The K-major interpretation was verified by filling `A[m, k] = m % 16` and reading
back `tCrA[0..7]` for thread 0 (T0=T1=T2=0): observed `0 0 8 8 0 0 8 8`, matching
m_lo=0, m_hi=8. The naive M-major reading of `ALayout_64x16` (which would predict
`0 4 0 4 0 4 0 4` for that thread) is incorrect.

### 3.2 −128 fold and dequant arithmetic

The lop3 unpack of iter 08 computes `bf16(q + 128)` then subtracts 128 to recover
`bf16(q)`. Iter 09 deletes the explicit `−128` step and folds it into the host-side
`eff_zero`:

```
eff_zero_bf16 = bf16(z_int + 128)
out = (lop3_unpack_no_sub(q) − eff_zero) · scale
    = (bf16(q + 128)            − bf16(z + 128)) · scale
    = (q − z) · scale       (algebraically, when z, q are uint4)
```

This saves 4 HSUB2 per thread per k_block (the iter-08 `out -= 128` step).

Per thread per k_block, the dequant is **4 lop3 + 4 HSUB2 + 4 HMUL2**, with the
right pair (`*_lo` for h[0,2], `*_hi` for h[1,3]) routed to each `h[i]`:

```cpp
__device__ void
unpack_dequant_to_bf16(uint32_t packed,
                      uint32_t scale_lo_pair, uint32_t zero_lo_pair,
                      uint32_t scale_hi_pair, uint32_t zero_hi_pair,
                      nv_bfloat16 out[8])
{
    static constexpr uint32_t TEMPLATE = 0x43004300;
    static constexpr uint32_t MASK     = 0x000f000f;
    static constexpr uint32_t immLut   = (0xf0 & 0xcc) | 0xaa;

    uint32_t* h = reinterpret_cast<uint32_t*>(out);
    asm volatile("lop3.b32 %0,%1,%2,%3,%4;" : "=r"(h[0]) : "r"(packed),       "n"(MASK), "n"(TEMPLATE), "n"(immLut));
    asm volatile("lop3.b32 %0,%1,%2,%3,%4;" : "=r"(h[1]) : "r"(packed >> 4),  "n"(MASK), "n"(TEMPLATE), "n"(immLut));
    asm volatile("lop3.b32 %0,%1,%2,%3,%4;" : "=r"(h[2]) : "r"(packed >> 8),  "n"(MASK), "n"(TEMPLATE), "n"(immLut));
    asm volatile("lop3.b32 %0,%1,%2,%3,%4;" : "=r"(h[3]) : "r"(packed >> 12), "n"(MASK), "n"(TEMPLATE), "n"(immLut));

    nv_bfloat162* h2 = reinterpret_cast<nv_bfloat162*>(out);
    h2[0] = __hsub2(h2[0], reinterpret_cast<nv_bfloat162 const&>(zero_lo_pair));   // M=m_lo
    h2[1] = __hsub2(h2[1], reinterpret_cast<nv_bfloat162 const&>(zero_hi_pair));   // M=m_hi
    h2[2] = __hsub2(h2[2], reinterpret_cast<nv_bfloat162 const&>(zero_lo_pair));   // M=m_lo
    h2[3] = __hsub2(h2[3], reinterpret_cast<nv_bfloat162 const&>(zero_hi_pair));   // M=m_hi
    h2[0] = __hmul2(h2[0], reinterpret_cast<nv_bfloat162 const&>(scale_lo_pair));
    h2[1] = __hmul2(h2[1], reinterpret_cast<nv_bfloat162 const&>(scale_hi_pair));
    h2[2] = __hmul2(h2[2], reinterpret_cast<nv_bfloat162 const&>(scale_lo_pair));
    h2[3] = __hmul2(h2[3], reinterpret_cast<nv_bfloat162 const&>(scale_hi_pair));
}
```

## 4. WGMMA kernel: pipelines and main-loop structure

Two pipelines:

| Pipeline | Period | Stages | Per-stage size | Class |
|---|---|---|---|---|
| A/B (existing) | 1 k_tile | 3 | ~36 KB | `PipelineTmaAsync<3>` (unchanged) |
| **SZ (new)** | 1 group = 2 k_tiles | 2 | 128 uint32 = 512 B | `PipelineTmaAsync<2>` |

Total extra smem: ~1 KB (SZ stages) + small SZ pipeline barrier storage.

### 4.1 Producer (warpgroup 2)

Outer loop over groups, inner loop over the 2 k_tiles per group:

```
while linear_idx < total_tiles:
  for k_group in 0..k_group_count:
    sz_pipeline.producer_acquire(sz_pipe_write)
    src = d_sz_packed + k_group * M + m_idx * 128            # uint32 units
    SM90_BULK_COPY_G2S: 512 B from src -> smem.SZ[stage]
    ++sz_pipe_write

    for k_tile_in_group in 0..2:
      ab_pipeline.producer_acquire(ab_pipe_write)   # unchanged from iter 08
      issue A bulk copy + B TMA                     # unchanged
      ++ab_pipe_write

  linear_idx += grid_size
```

`transaction_bytes` for the SZ barrier = 512.

### 4.2 Consumer (warpgroups 0, 1)

Iter-08 prologue + main-loop + tail are preserved verbatim. The only addition is a
4-LDS + 4-PRMT block that runs once per group (at every even `k_tile_iter`) and
caches the 4 working pairs in registers:

```
for k_tile_iter in 0..k_tile_count:
  if k_tile_iter % 2 == 0:                          # group boundary
    sz_pipeline.consumer_wait(sz_pipe_read)
    {r0,r1,r2,r3} = LDS.32 from sz_smem[stage] at {m_0, m_0+4, m_0+32, m_0+36}
    {lo_pair_s, lo_pair_z, hi_pair_s, hi_pair_z} = PRMT(r0..r3)
    sz_pipeline.consumer_release(sz_pipe_read)
    ++sz_pipe_read

  if k_tile_iter == 0: iter-08 PROLOGUE (load_k_block uses cached pairs)
  else:                iter-08 MAIN-LOOP iteration

iter-08 TAIL (drain, release last A/B stage)
```

`load_k_block` becomes:

```cpp
auto load_k_block = [&](int kb, int stage) {
  uint32_t* smem_base = smem.A.begin() + stage * a_stage_elements + wg_id * 512;
  uint32_t packed = smem_base[local_tid + kb * 128];
  unpack_dequant_to_bf16(packed,
                         lo_pair_s, lo_pair_z, hi_pair_s, hi_pair_z,
                         reinterpret_cast<nv_bfloat16*>(tCrA.data() + kb * size<0>(tCrA)));
};
```

The cached pair-uint32s persist across the 2 k_tiles inside a group (cost: 4 regs
per thread). `m_0` etc. are derived from `threadIdx.x` once at kernel start.

### 4.3 Unchanged from iter 08

- B TMA path
- 3-stage A/B pipeline geometry
- k_block interleaving with `wait<2>`, delayed stage release at `k_block == 1`,
  `consumer_try_wait` prefetch in the main loop
- Tail drain + last-stage release
- Deferred `tma_store_wait<0>` epilogue
- Threadblock swizzling default (`log_swizzle = 0`)

## 5. Validation plan

CPU reference uses raw integer `q` and `z` (avoids double-counting bf16 rounding):

```cpp
for m, n:
  sum = 0.f
  for k:
    g = k / 128
    sum += float(q_int[m,k] - z_int[g,m]) * float(scales[g,m]) * float(B[n,k])
  ref[m,n] = alpha * sum + beta * float(C[m,n])
```

GPU kernel computes `(bf16(q+128) − bf16(z+128)) · bf16_scale`, which is bit-exactly
equivalent for the (q − z) sub when q, z ∈ [0,15] (both fit exactly in bf16).

Tolerance: `max_err < K · 0.05`. Tune in implementation if too loose/tight; document
the final value.

Test list: see §1.

## 6. Performance expectations

| Size | Iter 08 | Iter 09 target |
|---|---|---|
| 4096³ | 704 TFLOP/s (86.7% cuBLAS) | ≥ 690 TFLOP/s (≥ 85%) |
| 8192³ | 699 TFLOP/s (94.4% cuBLAS) | ≥ 685 TFLOP/s (≥ 92%) |

Added work (per thread per k_block): 4 HSUB2 + 4 HMUL2 vs. iter 08's 4 HSUB2 (the
−128 step) — net +4 HMUL2 / k_block, amortized over WGMMA. Group-boundary cost: 4
LDS.32 + 4 PRMT, once per 8 k_blocks. Producer adds one `SM90_BULK_COPY_G2S` of
512 B per group.

## 7. Risks

1. **SZ-pipeline stall.** If 2 stages aren't enough, the consumer's group-boundary
   `consumer_wait` will starve WGMMA. Bump to 3 stages (+512 B smem) if profiling
   shows it.
2. **Tolerance tuning.** Random `scale ∈ [0.25, 4.0]` enlarges output magnitude vs.
   iter 08. `K · 0.05` is a starting bound; adjust if it's too loose/tight.
3. **`m_lo` / `m_hi` derivation bookkeeping.** Off-by-one risk in `(local_tid/4)%8 + 16*(local_tid/32)`. Mitigation: derive once from `threadIdx.x`, named constants. Also: the underlying CuTe `ALayout_64x16` codomain is K-major (not M-major as a naive reading might suggest); always verify mapping empirically when porting to a new MMA atom (test from §3.3).
4. **Host pack endianness.** Each `sz_smem` uint32 must have scale in low halfword and eff_zero in high halfword. Host pack helper has one explicit definition (`(z_bits << 16) | s_bits`) and a unit test on a 1-element interleave.
5. **`unpack_u4_to_bf16` divergence.** Iter 08's helper still subtracts 128. Iter
   09 introduces `unpack_dequant_to_bf16` in a new header; iter 08 binary stays
   untouched.
