# Design: Prefix caching for VLM (native Qwen3.5 ViT) in TurboMind

- Date: 2026-06-29
- Status: Approved design, pre-implementation
- Scope: TurboMind C++ engine + the Python serving/enablement glue for the
  **native Qwen3.5 C++ ViT** VLM path.

## 1. Goal & core problem

**Goal.** Enable TurboMind prefix caching for the **native Qwen3.5 C++ ViT** VLM
path — the path that carries raw pixel tensors in `Sequence::multimodal_inputs`
and runs the vision encoder in-engine. Legacy Python-embedding VLMs, audio, and
the PyTorch backend are out of scope.

**Core problem.** TurboMind keys prefix blocks purely on token IDs (`PrefixKey` =
cumulative token-ID hash + parent identity + exact token comparison, in
`src/turbomind/engine/`). Every image placeholder position carries the *same*
`image_token_id`, repeated N times, so token-only identity cannot distinguish two
different images of equal token length — naive VLM caching produces false hits
(one image's KV reused for a different image). This is why VLM prefix caching is
force-disabled for TurboMind at `lmdeploy/serve/core/vl_async_engine.py:33-38`.

**Solution (single correctness mechanism).** Fold a per-image **fingerprint**
(carried in the request's multimodal input; *generated by a later PR*, consumed
here) into the trie identity of the **first block of each image** — the block
where the image starts. The cumulative prefix hash and the parent-identity chain
propagate that identity to the image's remaining blocks for free; one exact
fingerprint compare at the first block guards hash collisions.

No span clamp is needed: resuming inside an image span is correct because the ViT
is deterministic and re-runs for any image overlapping the forward window, while
the cached head KV came from those same embeddings.

**Fingerprint semantics.** An opaque, equality-comparable value. Distinguishing
images is entirely the generator's job (later PR); this PR's matcher only
compares. An **empty fingerprint never compares equal to anything, including
another empty fingerprint**. Until real fingerprints exist, matching simply fails
at an image's first block and image-span reuse stays dormant (only text before
the first image is reused).

## 2. Fingerprint type & data plumbing

The fingerprint is **256-bit (SHA-256)** data, stored as four 64-bit words.

New shared low-level header `src/turbomind/engine/fingerprint.h`:

```cpp
#pragma once
#include <array>
#include <cstdint>

namespace turbomind {

// 256-bit (SHA-256) opaque multimodal content identity, stored as four 64-bit
// words. All-zero is the reserved "empty" sentinel; an empty fingerprint never
// compares equal to anything -- including another empty fingerprint.
struct Fingerprint {
    std::array<uint64_t, 4> words{};

    bool empty() const noexcept { return words == std::array<uint64_t, 4>{}; }

    friend bool operator==(const Fingerprint& a, const Fingerprint& b) noexcept
    {
        if (a.empty() || b.empty()) {
            return false;
        }
        return a.words == b.words;
    }
    friend bool operator!=(const Fingerprint& a, const Fingerprint& b) noexcept { return !(a == b); }
};

}  // namespace turbomind
```

Hash fold helper added near `HashCombine` in `prefix_key.h` (folds all 4 words):

```cpp
inline size_t HashCombine(size_t seed, const Fingerprint& fp) noexcept
{
    for (uint64_t w : fp.words) {
        seed = HashCombine(seed, static_cast<size_t>(w));
    }
    return seed;
}
```

Plumbing chain (one field, default empty):

- `src/turbomind/models/qwen3_5vit/qwen3_5vit_input.h` — add
  `Fingerprint fingerprint{};` to `Qwen3_5VitItem` (+ ctor arg defaulted to `{}`).
- `src/turbomind/python/bind.cpp` (lines 347-368) — accept the SHA-256 digest as
  `py::bytes` in the `Qwen3_5VitItem` init (length 0 = empty, length 32 =
  `std::memcpy` into `fp.words.data()`, otherwise raise); expose a `fingerprint`
  property that reads back 32 `py::bytes` and validates on write.
- `lmdeploy/turbomind/models/qwen3_5.py::to_turbomind_multimodal` (lines 404-411)
  — pass `fingerprint=input_mm.get('fingerprint', b'')` (`b''` = empty until the
  generation PR).

> `MultiModalData` (in `models/vision_model.h`) does **not** gain a fingerprint
> field — nothing in the ViT forward uses it. The fingerprint flows from
> `Qwen3_5VitItem` straight into the engine-visible projection (Section 4).

Sentinel note: all-zero (or `b''`) is "empty". A real SHA-256 digest is never
all-zero, so no remap is required.

## 3. Prefix-key integration (first-block fingerprint)

Terminology: a block's *start-fingerprints* = the fingerprints of images whose
**start token** falls inside that block (ordered by start). Almost every block
has an empty list; a block fully *inside* an image (not where it starts) also has
an empty list — its identity is carried by the cumulative hash + parent chain.

**(a) `LogicalBlock` storage** — `block.h`:

```cpp
struct LogicalBlock {
    // ...existing fields...
    std::vector<int>         tokens;
    std::vector<Fingerprint> image_fps;  // NEW: start-fingerprints (usually empty)
};
```

**(b) `ExtendPrefixKey` overload** — `prefix_key.h` (folds tokens, then each
start-fingerprint):

```cpp
inline PrefixKey ExtendPrefixKey(PrefixKey key, TokenSpan tokens, const std::vector<Fingerprint>& fps)
{
    key = ExtendPrefixKey(key, tokens);   // existing token fold
    for (const Fingerprint& fp : fps) {
        key.hash = HashCombine(key.hash, fp);
    }
    return key;
}
```

**(c) `PrefixTrie::Find` exact compare** — identity = parent + tokens +
start-fingerprints (direct `std::vector<Fingerprint>` compare):

```cpp
LogicalBlock* Find(const LogicalBlock* parent, const PrefixKey& key,
                   TokenSpan tokens, const std::vector<Fingerprint>& fps) const
{
    if (auto it = index_.find(key); it != index_.end()) {
        LogicalBlock* b = it->second;
        if (b->parent == parent && b->size == tokens.size
            && std::equal(tokens.begin(), tokens.end(), b->tokens.begin())
            && b->image_fps == fps) {   // vector==, empty fp never equal
            return b;
        }
    }
    return nullptr;
}
```

Because `Fingerprint::operator==` is false whenever either side is empty, a block
where an un-fingerprinted image starts can never match — `Find` returns null and
matching halts there.

**Contract compliance (`prefix-identity`).** Continuation blocks keep empty
`image_fps` and token-only exact compare, but they're only reachable via
`Find(parent=first_block, …)`, and the first block's exact compare includes the
fingerprint. So image identity is exact through the parent chain — never
hash-only. The cumulative `PrefixKey` only does bucketing.

**(d) Matching** — `MatchPrompt` (`scheduler.cc:304-326`) passes start-
fingerprints; halt is automatic (different image / empty fp / token miss all
`break`). See Section 4 for how `fps` is produced.

**(e) Indexing** — `CreateMissingBlocks` (`scheduler.cc:328-359`) folds start-
fingerprints into the key and stores them on the block; normal indexing with the
existing collision fallback. No special handling for empty fingerprints: an
indexed-but-unmatchable block past an empty fingerprint is harmless dead weight
(matching halts before it via `Find`).

```cpp
if (size == bs) {
    const auto next = ExtendPrefixKey(st.key, tokens, fps);
    x.parent    = st.parent;
    x.key       = next;
    x.size      = size;
    x.tokens.assign(tokens.begin(), tokens.end());
    x.image_fps = fps;                       // usually empty
    if (!trie_.Insert(x)) {
        LogCollision(s, CollisionSite::kAccept, offset, offset + size);
        x.parent = nullptr; x.key = {}; x.size = 0; x.tokens.clear(); x.image_fps.clear();
    }
    else {
        st.parent = h.get();
        st.key    = next;
    }
}
```

**(f) Partial-block `Search`** (used only when the `cache_prompt_boundary` / fork
features are enabled — off by default) must fold and exact-compare start-
fingerprints the same way. With the boundary knobs off (default), this path is
inactive; no default-config behavior change.

**(g) `PublishGeneration` indexing** (`scheduler.cc:711`) is a third indexing
site and must fold the same way. `CreateMissingBlocks` leaves the prompt-tail
block private when `size < bs`; once generation extends the sequence,
`PublishGeneration` indexes that block as a **full** block (`[prompt tail] +
[first generated tokens]`), and a later multi-turn request whose longer prompt
re-includes that span matches it via `MatchPrompt`. An image start can only fall
in this prompt-tail block — generated positions never carry one — so the folding
is guarded by `x.offset < s.prompt_len` and scans just that block. Without it the
published node would be token-only, diverging from the identity `Accept` rebuilds:
that both loses legitimate reuse and, in narrow token-alignment cases (an image
starting at the prompt-tail block boundary), risks a false hit against a different
image's KV. Folding makes the identity (token + parent + image-start fingerprint)
uniform across **all** lookup and indexing sites, so the safety does not rely on
the native-path "image_token_id ⇔ span start" invariant.

## 4. Deriving start-fingerprints from the sequence

`MultiModalData` must stay **opaque** to the engine. The engine already holds
`Sequence::multimodal_inputs` as forward-declared `shared_ptr`s it never
dereferences (`request.h:141,248`). We add a lightweight, engine-visible
**projection** of just `(interval, fingerprint)`, populated by the vision module.

**(a) Engine-local span type** — `engine/request.h` (needs only
`core/interval.h` + `engine/fingerprint.h`, no model deps):

```cpp
// The prefix-cache projection of one multimodal input: its token span and
// content identity. The engine never sees MultiModalData / pixels.
struct MultiModalSpan {
    Interval    interval;     // absolute token span [begin, end)
    Fingerprint fingerprint;  // empty until generation PR
};
```

**(b) `Sequence`** keeps `multimodal_inputs` opaque and adds the projection:

```cpp
std::vector<MultiModalSpan> multimodal_spans;  // engine-visible; consumed by scheduler
std::vector<std::shared_ptr<MultiModalData>> multimodal_inputs;  // opaque (unchanged)
```

**(c) Vision module fills both during `kAdd`** — `qwen3_5vit.cc::Add`
(lines 227-229):

```cpp
const Interval interval{item.token_begin, Interval::Size{tokens}};
s.multimodal_inputs.push_back(std::make_shared<MultiModalData>(
    MultiModalData{item.data, interval, item.grid_thw}));
s.multimodal_spans.push_back(MultiModalSpan{interval, item.fingerprint});
```

`kAdd` runs at `engine.cc:402`, before `scheduler_.Accept()` at `engine.cc:406`,
so `multimodal_spans` is available to the scheduler during matching.

**(d) Cursor in `AcceptState`** — single advancing index, one monotonic pass over
`multimodal_spans` (which is prompt-ordered, ascending by start):

```cpp
struct AcceptState {
    // ...existing fields...
    size_t next_fp = 0;  // cursor into Sequence::multimodal_spans
};
```

**(e) `MatchPrompt`** — working copy, commit the cursor only on a matched block
(so the miss block's spans are not consumed before `CreateMissingBlocks`
recreates that block):

```cpp
for (; i < full_blocks; ++i) {
    const int offset = i * bs;
    size_t cur = st.next_fp;                 // working copy; do not commit on a miss
    std::vector<Fingerprint> fps;
    while (cur < s.multimodal_spans.size()
           && s.multimodal_spans[cur].interval.begin() < offset + bs) {
        fps.push_back(s.multimodal_spans[cur].fingerprint);
        ++cur;
    }
    const auto tokens = TokenSegment(s, offset, bs);
    const auto next   = ExtendPrefixKey(st.key, tokens, fps);
    if (LogicalBlock* b = trie_.Find(st.parent, next, tokens, fps)) {
        s.block_ids.emplace_back(b);
        st.parent  = b;
        st.key     = next;
        st.next_fp = cur;                    // commit advance only on a match
    }
    else {
        break;                               // cursor still at the miss block's first span
    }
}
```

**(f) `CreateMissingBlocks`** — continues the same cursor monotonically:

```cpp
for (int i = st.miss; i < all_blocks; ++i) {
    const int offset = i * bs;
    const int size   = std::min(prompt - offset, bs);
    std::vector<Fingerprint> fps;
    while (st.next_fp < s.multimodal_spans.size()
           && s.multimodal_spans[st.next_fp].interval.begin() < offset + size) {
        fps.push_back(s.multimodal_spans[st.next_fp].fingerprint);
        ++st.next_fp;
    }
    // ...create block; if (size == bs): fold fps into key + store x.image_fps + index; else private...
}
```

Condition note: we collect spans that **start** in the block
(`begin < offset+size`, with `begin >= offset` guaranteed by monotonic
consumption) — matching the first-block rule from Section 3. Coordinates are
absolute prompt positions on both sides.

Layering result: the engine/scheduler depend only on `Interval` + `Fingerprint` +
the engine-local `MultiModalSpan`. `MultiModalData` stays forward-declared and
opaque in the engine.

## 5. Eligibility & Python enablement

**(a) C++ eligibility — no functional change.** `Scheduler::PrefixEligible`
(`scheduler.cc:211-215`) already admits native multimodal requests (native leaves
`input_embeds`/`input_embeds_offsets` empty). Correctness now comes from
fingerprint folding, not from exclusion. Add a clarifying comment; keep the legacy
Python-embedding path excluded via the existing `input_embeds.empty()` check.

```cpp
bool Scheduler::PrefixEligible(const Sequence& s) const noexcept
{
    // Native VLM (multimodal_spans) is eligible: image identity is carried by the
    // per-image fingerprint folded into the prefix key. The legacy Python-embedding
    // path (input_embeds) stays excluded -- out of scope for this change.
    return enable_prefix_caching_ && !is_warm_up_ && s.input_embeds.empty() && s.input_embeds_offsets.empty()
           && s.token_ids != nullptr;
}
```

A request whose images all carry empty fingerprints is still *eligible*; it just
won't reuse image spans (matching halts at the first image), so text before the
first image can still be cached — the intended dormant-until-fingerprinted
behavior.

**(b) Python — relax the force-disable** in `vl_async_engine.py:33-38` to permit
TurboMind's native-vision path (`ImageEncoder` exposes `self.model`):

```python
if backend_config and backend_config.enable_prefix_caching:
    native_tm_vision = (backend == 'turbomind'
                        and getattr(self.vl_encoder.model, '_turbomind_native_vision', False))
    pytorch_new_preprocess = (backend == 'pytorch'
                              and getattr(self.vl_encoder, '_uses_new_preprocess', False))
    if not (native_tm_vision or pytorch_new_preprocess):
        backend_config.enable_prefix_caching = False
        logger.warning('Prefix caching is disabled for this VL model path. '
                       'Supported: TurboMind native-vision models and PyTorch new-preprocess '
                       'multimodal inputs.')
```

**(c) Unaffected guards.** The existing prefix-caching incompatibilities
(`engine.cc` step/logits/ppl checks; `async_engine.py:597,906`) are orthogonal to
multimodal and need no change.

## 6. Contract updates, testing, out-of-scope

**(a) Normative contract — `src/turbomind/engine/README.md`** (required by
`checklist.contract-sync`, updated in the same change):

- `contracts.prefix-identity` — extend identity to include image content:
  > Prefix identity is token identity, per-image content identity, plus parent
  > identity. Index lookup must use cumulative `PrefixKey`, exact parent identity,
  > exact segment-token comparison, and exact comparison of the block's
  > start-fingerprints (`LogicalBlock::image_fps`). A fingerprint is the image's
  > opaque 256-bit content identity; an empty fingerprint never compares equal to
  > anything, including another empty fingerprint. Blocks interior to an image
  > carry no fingerprint of their own — their identity is carried by the
  > cumulative key and the parent chain, since the image's first block
  > exact-compares the fingerprint. Hash equality alone is never identity.
- `contracts.prefix-prepare` — add: every indexing site folds each image's
  fingerprint into the cumulative key at the block where the image starts (from
  `Sequence::multimodal_spans`) and stores it on that `LogicalBlock` — `Accept`'s
  block creation, the partial-block `Search` when the boundary knobs are enabled,
  and `PublishGeneration` when it later indexes the prompt-tail block that block
  creation left private. The folding is uniform across lookup and indexing, so a
  published prompt-tail node has the same identity a future request's `Accept`
  rebuilds.
- Optionally a one-line `concepts` note that `Sequence::multimodal_spans` is the
  engine-visible `(token span, fingerprint)` projection, while
  `multimodal_inputs` stays opaque.

    Monkeypatch so each converter-input dict carries a content hash before
    `to_turbomind_multimodal`'s `input_mm.get('fingerprint', b'')` reads it:

    ```python
    import hashlib
    from lmdeploy.turbomind.models.qwen3_5 import Qwen3_5VisionModel
    _orig = Qwen3_5VisionModel.to_turbomind_multimodal
    def _patched(self, multimodal):
        for mm in multimodal:
            pv = mm.get('pixel_values', mm.get('pixel_values_videos'))
            mm['fingerprint'] = hashlib.sha256(
                pv.contiguous().cpu().numpy().tobytes()).digest()  # 32 bytes
        return _orig(self, multimodal)
    Qwen3_5VisionModel.to_turbomind_multimodal = _patched
    ```

    digest. This mirrors the future generator, so the test stays valid after it
    lands.

    1. Same image + identical prefix, twice → warm run shows scheduler
       `matched [0,M)` covering the image and `resume ... source=prefix`, and the
       ViT logs `batch_size == 0` (skip); output **token-identical** to the cold

**(c) Out of scope**

- **Fingerprint generation** — consumed here, produced by a later PR; everything
  ships with empty fingerprints (image-span caching dormant).
- Legacy Python-embedding VLM path, audio modality, PyTorch backend.
- Any new chunk/resume span-alignment logic — explicitly *not* needed (resuming

**(d) Risks / notes**

- Multi-image-per-block ordering relies on `multimodal_spans` being prompt-ordered
  (it is).
- mRoPE correctness: a reused prefix is byte-identical, so positions match; no
  extra handling.
- All-zero is the reserved empty sentinel; a real SHA-256 digest is never
  all-zero.

## 7. ViT skip for fully-cached images (the primary win)

- **Mechanism (no new logic).** The existing window-intersection filter in
  `Qwen3_5Vit::Setup` (`qwen3_5vit.cc:388-407`, `mm->interval & [history_len +
  inflight_input_len, +input_len)`) plus the `batch_size == 0` early-out in
  `Prepare`/`Forward` (`:515-517`, `:529-531`) skip encoding any image that does
  not overlap the active forward window. Section-3 fingerprint matching + the
  existing `Resume()`/`Schedule()` make `history_len` (= `resume_len`) advance
  past valid cached images, so the filter fires: no pixel copy, no ViT forward,
  no embedding patch. The only added code is one observability INFO log in
  `Setup` reporting images-batched / patches (`d.batch_size`) so the skip is
  assertable.
- **Skip condition.** Image fully covered by `resume_len` **and** its blocks are
  valid (`is_valid`, published by the producer). Partial coverage (resume
  mid-span) or an unpublished producer → ViT re-runs for the whole image and
  patches only the in-window tail (correct, per Section 1).
- **Rare edge case (acceptable, no special handling).** If an image is the literal
  tail of the prompt with no trailing text and the entire prompt is a cache hit,
  the executable-context cap forces `resume_len = prompt_len - 1`, so the last
  (image) token is reprocessed and that image's ViT runs. With any trailing text
  (the normal question) the image sits fully below `resume_len` and is skipped.
- **Verification.** Covered by Section 6 mechanism test (1)'s ViT-skip assertion,
  which guards against regressions where `history_len` fails to advance.

## Data flow summary

```
Qwen3_5VitItem.fingerprint (py::bytes, SHA-256 digest)
  -> [kAdd] Sequence.multimodal_spans[] = {interval, Fingerprint}
  -> [Accept] MatchPrompt/CreateMissingBlocks (+ PublishGeneration for the
     prompt-tail block): start-fingerprints folded into PrefixKey at the image's
     first block; LogicalBlock.image_fps stored; exact compare in PrefixTrie::Find
  -> [Resume/Schedule] valid matched image blocks raise resume_len/history_len
  -> [Qwen3_5Vit::Setup/Forward] window-intersection filter skips ViT for images
     fully below history_len
```
