# Folded SM90 MXFP4 × FP8 packing and dequantization

This note describes the folded W4A8 path implemented by:

- `src/turbomind/kernels/gemm/sm90_mixed_pack.cu`
- `src/turbomind/kernels/gemm/sm90_mixed_pack.h`
- `src/turbomind/kernels/gemm/gemm_universal_sm90_mxfp4_fp8_folded.h`

The persistent weight is MXFP4 E2M1 at exactly four bits per value. The
activation and the register-source WGMMA weight operand are E4M3. Every K128
weight tile has four K32 group scales and one folded K128 base scale.

## Persistent representation

For a source E2M1 weight `wi`, let `Mi` be its three magnitude bits and `Si`
its sign bit. The weight packer processes 16 values per WGMMA lane and emits
two `uint32_t` words:

```text
63                                  32 31                                   0
┌──────── packed[1]: w8..w15 ─────────┬───────── packed[0]: w0..w7 ──────────┐
└─────────────────────────────────────┴──────────────────────────────────────┘
```

Each word contains eight weights. Magnitudes retain their native nibble
positions, while signs are cross-packed into positions useful to E4M3:

```text
nibble     7      6      5      4      3      2      1      0
content  S3|M7  S7|M6  S2|M5  S6|M4  S1|M3  S5|M2  S0|M1  S4|M0
```

The packer implements this layout directly:

```cpp
uint32_t packed = 0;
for (int j = 0; j < 8; ++j) {
    const uint16_t bits = source[word * 8 + j];
    packed |= uint32_t(bits & 0x7u) << (4 * j);

    const int sign_slot = j < 4 ? 2 * j + 1 : 2 * (j - 4);
    packed |= uint32_t(bits & 0x8u) << (4 * sign_slot);
}
```

Consequently:

- `S0..S3` occupy bits `7, 15, 23, 31`, which are already the sign bits of
  four E4M3 bytes.
- `S4..S7` occupy bits `3, 11, 19, 27`; shifting left by four puts them in the
  sign bits of four E4M3 bytes.
- Sixteen weights occupy 64 bits and are loaded by one `LDS.64` per lane and
  K32 group.

## Folded scale representation

One folded record covers 64 output rows and four K32 groups. The packer scans
the 256 source UE8M0 scale bytes and computes:

```cpp
base_code = minimum_finite_ue8m0_exponent;
shift     = source_ue8m0_exponent - base_code;
```

A record is foldable only when all exponents are finite and:

```text
maximum exponent - minimum exponent <= 6
```

The relative K32 scale remains an eight-bit value. The packer stores the
ready-to-add E4M3 exponent-field delta:

```cpp
uint8_t relative_scale = uint8_t(shift << 3);
```

The two output rows owned by a WGMMA row pair are adjacent and loaded
together:

```cpp
uint16_t scale_pair = uint16_t(shift_lo << 3)
                      | uint16_t(shift_hi << 11);
```

Thus the low and high bytes are still two independent eight-bit scales. The
relative-scale plane contains 256 bytes per record and is loaded through TMA.

The K128 base exponent is stored separately as a signed unbiased byte:

```cpp
int8_t base_exponent = int8_t(base_code - 127);
```

The base plane uses a 16-byte record for aligned `cp.async`; only its first
byte is the exponent.

## Scale-adjusted E4M3 lookup tables

The positive E2M1 magnitude codes have the following exact E4M3 encodings:

| E2M1 code | Value | E4M3 byte |
| ---: | ---: | ---: |
| 0 | 0 | `0x00` |
| 1 | 0.5 | `0x30` |
| 2 | 1 | `0x38` |
| 3 | 1.5 | `0x3c` |
| 4 | 2 | `0x40` |
| 5 | 3 | `0x44` |
| 6 | 4 | `0x48` |
| 7 | 6 | `0x4c` |

E4M3 has three mantissa bits, so adding one to its exponent field is an
integer addition of `0x08`. Since the packed relative scale is already
`shift << 3`, it is also the byte offset of one eight-byte lookup table. At
CTA startup, seven single-row tables are materialized in the otherwise-unused
epilogue staging region:

```cpp
struct Table { uint32_t values0_to_3, values4_to_7; };
Table tables[7];  // 56 bytes
```

Each lane uses the low and high scale bytes as direct offsets and loads the
two row tables with two aligned `LDS.64` operations. Equal table addresses
broadcast within a warp; distinct shifts occupy distinct two-bank pairs.
Byte zero is masked out when initially constructing each table, so E2M1 zero
remains exact zero. The four loaded registers represent these two eight-entry
tables:

```text
row_lo: 00, 30+dlo, 38+dlo, 3c+dlo, 40+dlo, 44+dlo, 48+dlo, 4c+dlo
row_hi: 00, 30+dhi, 38+dhi, 3c+dhi, 40+dhi, 44+dhi, 48+dhi, 4c+dhi
```

For each K32 group, every lane loads the `uint16_t` scale pair for its WGMMA
row pair, then loads the two selected tables. The shared loads naturally
broadcast across the four lanes that use the same row pair. No register
shuffle is used in this path.

## Register dequantization

For each K32 group, one `LDS.64` produces two packed words containing 16 E2M1
weights. Each word is decoded into two registers of four E4M3 bytes:

```cpp
constexpr uint32_t kMagnitudeSelectors = 0x00007777u;
constexpr uint32_t kE4m3Signs = 0x80808080u;

const uint32_t lo_selector = packed & kMagnitudeSelectors;
const uint32_t hi_selector = (packed >> 16) & kMagnitudeSelectors;

const uint32_t lo_value =
    prmt(tables.values0_to_3_lo, tables.values4_to_7_lo, lo_selector);
const uint32_t hi_value =
    prmt(tables.values0_to_3_hi, tables.values4_to_7_hi, hi_selector);

const uint32_t row_lo = lo_value | (packed & kE4m3Signs);
const uint32_t row_hi = hi_value | ((packed << 4) & kE4m3Signs);
```

Each selector nibble is an index from zero through seven. `PRMT` performs four
independent byte selections, converting four magnitudes in one instruction.
The cross-packed signs are then inserted without a sign lookup.

Two packed words produce the native four-register E4M3 WGMMA fragment:

```text
out[0] = {w0,  w1,  w2,  w3}    row_lo, K offset 0
out[1] = {w4,  w5,  w6,  w7}    row_hi, K offset 0
out[2] = {w8,  w9,  w10, w11}   row_lo, K offset 16
out[3] = {w12, w13, w14, w15}   row_hi, K offset 16
```

This is repeated for the four K32 groups in a K128 stage. For each WGMMA
output atom, the resulting E4M3 register fragments are consumed by four
`QGMMA ... K32` operations. The hot dequantization path uses fixed loads,
masks, shifts, and `PRMT`; it does not rely on data-dependent branches or
comparisons.

## Applying the folded base scale

The per-group relative scale is already present in the E4M3 weight bytes
before WGMMA. The common K128 base scale is not applied to the weight bytes.
After the four K32 contributions have accumulated into the K128 scratch
fragment, the kernel injects the signed base exponent into the positive FP32
activation scale:

```cpp
uint32_t bits = __float_as_uint(activation_scale);
uint32_t delta = static_cast<uint32_t>(base_exponent) << 23;
float folded_scale = __uint_as_float(bits + delta);
```

The scratch fragment is then merged into the persistent accumulator with one
FMA per accumulator element:

```cpp
accumulator = fmaf(k128_scratch, folded_scale, accumulator);
```

Therefore the scale application order is:

```text
4-bit E2M1 weight
    -> E4M3 lookup with its K32 relative scale
    -> E4M3 × E4M3 WGMMA
    -> apply the folded K128 base scale once to the K128 contribution
    -> merge into the persistent FP32 accumulator
```
