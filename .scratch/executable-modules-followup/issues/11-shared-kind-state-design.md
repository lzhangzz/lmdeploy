# 11: Shared per-rank kind state vs per-layer modules — the open design question

> *This was generated by AI during triage.*

**What:** consolidates issues 01, 06, and 07 per maintainer (2026-09-20).
The executable-modules refactor gives every layer its own module while
cross-layer execution state lives in one shared per-rank kind state
(`AttentionState`, `MoeDefaultState`/`MoeDeepEPState`, `DeltaNetState`),
rendezvoused during the bind walk. Three unresolved symptoms of one
question:

- **07 → coordination.** Batch-level setup work (shared slot fills) runs
  under a wave-stamp guard the maintainer rejects: implicit coordination
  whose correctness depends on a shadow copy of the engine's op sequencing
  (`kForward` does not tick the wave). DeltaNet already uses a conflicting
  mechanism (layer-0 gate for kPrepare batch work) alongside the wave —
  two answers to one question in one module.
- **06 → sizing.** The shared state is sized and gated from the first-bound
  module (exemplar) while modules forward with their own configs;
  uniformity is assumed everywhere and checked nowhere. Maintainer: "the
  problem is much deeper than it seems."
- **01 → membership.** Vision-tree Attention modules join the bind walk and
  share the text AttentionState; walk-order dependent and accidental rather
  than designed.

**The design question:** what belongs to the per-rank shared state, what
belongs to per-layer modules, and how does batch-level work get dispatched
once per pass. The candidate replacement already present in our
abstraction: the shared kind state itself is the batch-level recipient —
the engine hands setup to the state once, then walks the modules for
per-layer work. Ownership explicit; no stamps, no cadence assumption, no
exemplar-first-wins sizing story left implicit.

**Direction:** grill-with-docs into shape, then a spec. Do not implement
piecemeal fixes from 01/06/07 while this is open.
