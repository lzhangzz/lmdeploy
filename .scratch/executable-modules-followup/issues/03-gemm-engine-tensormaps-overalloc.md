# 03: GEMMEngine over-allocates the tensormaps workspace

**What:** the `GEMMEngine` ctor
(src/turbomind/models/llama/GEMMEngine.cu) sets
`workspace_.tensormaps_size = 8192 * 128` (~1 MiB, "maximum 4096 tensor
maps") but allocates `workspace_.tensormaps` with `workspace_.partials_size`
(tens of MiB). Moved verbatim from the retired `LlamaLinear.cu`, so the
waste predates the executable-modules effort — not a regression, just free
VRAM burned on every rank at engine creation.

**Direction:** allocate with `tensormaps_size` after confirming no kernel
writes past 1 MiB of tensor-map space.

**Category:** bug
**Status:** resolved

## Agent Brief

**Category:** bug
**Summary:** tensor-map workspace: raise the contract to 16k×128 and allocate it exactly

**Current behavior:** the per-rank GEMM engine declares the tensor-map
contract as `tensormaps_size = 8192 * 128` (~1 MiB; the size comment
understates the slot count) but allocates the buffer with `partials_size`
(32 MiB). Most kernel families bound-check their TMA workspace needs
against `tensormaps_size` before use; the plain SM90 path passes the buffer
into TMA-descriptor preparation and the kernel launch with no visible bound
check.

**Desired behavior:** `tensormaps_size` becomes `16384 * 128` (2 MiB, double
the current contract), the size comment is corrected to match reality, the
engine allocates exactly `tensormaps_size`, and every consumer of the
tensor-map workspace checks its byte need against `tensormaps_size` and
fails loudly on overrun.

**Key interfaces:**
- The GEMM engine workspace construction: sizes and allocation
- The plain-SM90 kernel-impl TMA path: add the bound check its sibling
  families already have
- No kernel behavior or family-selection changes

**Acceptance criteria:**
- [ ] `tensormaps_size = 16384 * 128` with a correct comment; allocation
      equals it (2 MiB, ~30 MiB/rank recovered)
- [ ] Every tensormaps consumer is grep-verifiably bound-checked
- [ ] Build green; GEMM warm-up plus a model gate (at least 128 meaningful
      tokens)

**Out of scope:** barriers/partials sizing; family selection.

## Answer

Implemented as briefed with the maintainer amendment (2026-09-20):
`tensormaps_size` is now `16384 * 128` (2 MiB) with a corrected slot
comment (a `CUtensorMap` is 128 B, so the buffer holds up to 16k maps —
the old comment's "4096" undercounted the 8192-slot contract), and the
engine allocates exactly `tensormaps_size` instead of `partials_size`
(~30 MiB recovered per rank). The plain-SM90 grouped path gained the
bound check its sibling families already had: before
`Gemm::PrepareTmaDescs`, `num_groups * Gemm::kTmaDescNum *
sizeof(CUtensorMap) + (num_groups + 1) * sizeof(int)` is checked against
`tensormaps_size` — the same formula the bf16/mixed/mxfp4 families use,
verified against the `prepare_moe_tma_descs_sm90_fp8` write pattern (4
descs/group blocked-A, 2/group indexed-A via `Gemm::kTmaDescNum`, plus a
`num_groups + 1`-entry offsets tail). Grep-verified complete consumer
set behind checks: sm90, sm90_bf16, sm90_mixed, sm90_mxfp4_fp8
(`tma_workspace_bytes`), cublas (`total_bytes`); launch-arg passes hand
the kernel the same region the adjacent check sized.

Gate: `ninja` clean; GEMM warm-up plus `Qwen/Qwen3.5-35B-A3B-FP8` tp=1
via `scripts/test_turbomind_model.py` — 256/256 meaningful tokens,
exit 0.
