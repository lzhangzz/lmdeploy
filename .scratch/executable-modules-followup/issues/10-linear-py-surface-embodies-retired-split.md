# 10: linear.py surface must mirror the merged module — one Linear, weight included

> *This was generated by AI during triage.*

**What:** the executable-modules refactor merged weight storage and forward
execution into one C++ module (params + Forward + planning on `Linear`), but
the standalone Python surface kept the retired two-concept shape: a `Linear`
factory whose execution methods take a separate `Weight` handle
(`linear(x, weight, exec_plan=...)`), internally delegating to the weight's
own module. The API presents "executor consumes data"; underneath, the
prepared handle executes itself. Maintainer (2026-09-20): wrong and
inconsistent with the refactor's goal.

**Settled direction (maintainer-approved 2026-09-20):**

- ONE `Linear` class in Python, mirroring the C++ module: per-weight, params
  on the instance, executes itself. `Weight` retires; no wrapper, no second
  prepared-handle class.
- Grouped is construction config on the same class (offsets/indices in the
  call), exactly as dense-vs-grouped is a config axis of the C++ `Linear`.
- The per-device thing is the engine, not a Linear — C++ has no device-bound
  Linear: `LlamaLinear` retired, the per-rank `GEMMEngine` lives in
  `turbomind::Context` (`linear_engine()`). Python mirrors this as an
  ambient per-device engine the Linear binds to. A `get_linear()`-style
  accessor, if kept, corresponds to the engine/Context — never to a Linear.
- The public contract is NOT redesigned: same operation names and arguments
  as pre-refactor — `prepare_weight`/`fuse_weight` take the same tensors and
  land them on the instance, `get_exec_plan(x)` probes the same, execution
  takes `x` plus exec plan, `tune` keeps its role. Same what-you-pass /
  what-you-get; the fix is representation, not API.
- The per-weight Linear structurally pins its device engine, so issue 05's
  dangle cannot arise in this shape; 05 closes when this lands.

**Rejected alternatives (recorded so they stay rejected):**

- Three-class split (`LinearEngine` / `Linear` / `LinearExperts`) —
  re-encodes the executor/data split with more names.
- PyTorch `nn.Linear`-style construct/load/process ceremony — copying an
  external style; "do not copy the style, do what best suits our
  abstraction".
- Keeping the facade and returning raw module handles — still two concepts;
  "with weight merged into linear" there is nothing to return from prepare
  and pass to execute.

**Open at implementation time:** construction signature; where records
import/export and measure-mode control live (engine accessor); consumer
migration (PyTorch AWQ backend, tests/turbomind/linear — mechanical, call
sites keep their shape).

**Direction:** settled as above; next step is an implementation brief or
spec before any agent work.
